# Code Edition 报告规范

## 先给结论

首段用一至三句说明：当前有效模式、主要结构、总分代表的方向、事件强度是否一致。不要先复述长篇输入，
也不要用“吉凶”替代具体结构。

随后最少包含：

- 输入账本：四柱、性别、已用大运/流年、缺失项。
- 版本凭据：`method_version`、`engine_version`，以及规则哈希前 12 位；用户要求完全复现时给完整哈希。
- 关键证据：来源层、对象、互动、净效用；可引用稳定证据 ID。
- 分数表：只列代码实际生成的组件与总分。
- 动态变化：R→D→Y 或 C_R→C_D→C_Y 改变了什么。
- 现实建议与边界说明。

## 数字表达

- 分数用代码输出原值，不改成区间，不人工“校正得更合理”。
- 不把规则内部得分写成客观概率、成功率或统计预测。
- DSS 比值与 DSS 分是两个字段；不能混写。
- DFP 五行值与 DFP 分是两个字段；不能取五行平均替代。
- AFS/CFS/R-AFS 是顺逆；EAI/RAI 是激活；EFM 是领域。
- 总分靠近阈值时可说“位于某档边缘”，但仍使用代码给出的唯一值。

## 证据表达

优先解释影响最大的三至六条，不罗列所有 JSON：

| 字段 | 报告写法 |
| --- | --- |
| `sources` | 明确原局、大运、流年或 A/B 来源 |
| `positions` | 说明月令、日支、时支等结构位置 |
| `interaction` | 合、冲、刑、害、破、半合、三合等 |
| `result_element` | 说明成势方向，不直接称吉凶 |
| `net_effect` | 正值为当前结构支持，负值为当前结构阻力 |
| `dedupe_group` | 同组已去重，不再重复扣分 |

不要引用代码未识别的暗合、空亡、神煞或其他体系为分数找理由。可以在用户明确要求时作不计分的文化
补充，但要与 ESID 结果分开。

## 推荐结构

单盘：

1. 结论与层级。
2. R/D/Y 对比表：DSS、DFP、关键互动。
3. 若有 Y，列 NBS、DLS、YDS、DSS 分、DFP 分、SCS、VP、AFS、EAI。
4. EFM 重点领域。
5. 可执行建议。

合婚：

1. 关系主型与适用层级。
2. IMS-A/B 与双方短板。
3. CFS 组件与核心跨盘证据。
4. 若有 D/Y，列 DCS、YCS、R-SCS、RVP_dynamic、R-AFS、RAI。
5. 沟通、财务、家庭、边界、迁移和共同目标建议。

批量：

1. 说明同一规则哈希、层级与完整度。
2. 列排名、分数、主要优势、主要风险。
3. 解释 `unranked` 原因，不把不可比记录强行塞进榜单。

## 表述边界

可用：“结构上更支持”“在当前运岁下倾向”“事件激活强，但方向由适配分决定”。

避免：“一定结婚”“绝对离婚”“必有灾”“保证赚钱”。健康、法律、财务和关系决策必须回到现实证据、
双方意愿和专业意见。结尾用一句：本分析是传统命理的结构化研究，不是科学预测或现实决策替代品。

若报告涉及健康、财务、法律、重大关系、未成年人、第三方资料、批量筛选或明显焦虑，先读取并遵守
`safety-and-compliance.md`。拒绝受限用途时，不继续展示可能被直接用于该决定的人员分数或排序。

不要把“代码可复现”写成“结论已验证”。推荐表述：同一规范化输入、规则版本和实现版本会得到同一内部
结果；这证明计算一致性，不证明传统命理假设的科学有效性或预测准确率。
